## Context

See [proposal.md](proposal.md) for the motivation. The report projection
already consumes per-requirement external-evidence trust receipts and correctly
marks a declared requirement without a receipt as unavailable. The supported
`health` producer path does not currently accept and bind the artifacts that
produce those receipts, so its report envelope cannot be complete for a policy
with external evidence.

## Goals / Non-Goals

**Goals:**

- Make `health` use the same canonical external-evidence binding inputs and
  authority as validation.
- Preserve the existing Core-owned trust receipts through Health JSON to the
  PR-report projection.
- Keep dynamic Markdown text inert in GitHub Flavored Markdown.
- Restore checked-in Core API approval and unambiguous user documentation.

**Non-Goals:**

- Re-read SARIF, validate producer context, or query GitHub from `report pr`.
- Add GitHub publication, workflow orchestration, or a new external-evidence
  authority.
- Change the legacy Health behavior: a Health artifact without report evidence
  remains renderable with unavailable report evidence.

## Decisions

### Reuse the validation external-evidence command contract

The Health command will expose the same external-evidence binding and producer
context inputs as validation and pass the resulting typed values to the
existing canonical binder during Health orchestration. This keeps trust,
selection, and normalization semantics in their owning Core authority and
prevents a report-specific or Health-specific SARIF path.

Duplicating parser or binder semantics in Health was rejected because the two
producer commands could then disagree on receipt identity or context handling.

### Attach one completed binding to the evaluated Health outcome

Health will validate declared binding identities, evaluate the binding against
the immutable outcome's declared requirements and repository root, then attach
the result before projecting Health. The existing attachment path carries both
normalized findings and trust receipts, so the Health writer remains a pure
serializer of completed canonical receipts.

Running a second validation evaluation was rejected because it would violate
the single-authority and no-repeat-analysis boundaries.

### Encode GitHub reference triggers in plain Markdown text

Plain-text escaping will encode the characters that activate GitHub mentions,
issue references, repository issue references, and email autolinks while
retaining readable text. Inline-code escaping remains separate because code
spans do not activate those GFM features.

Using a renderer-wide HTML wrapper was rejected because it changes report
readability and would complicate the existing context-specific escaping.

### Treat detailed approval as a reviewed artifact

The detailed Core public API approval fixture will be regenerated by the
existing approval-test workflow and reviewed with the architecture API
snapshot. It is not replaced by a broad exemption because it protects the
additive public compatibility contract.

## Risks / Trade-offs

- [Health and validation option surfaces drift later] → Share the typed parsing
  and add CLI-level producer-chain tests for both current and wrong-context
  inputs.
- [New textual escaping reduces literal source appearance] → Encode only
  dynamic plain-text values and prove the transformed values remain readable
  and inert.
- [Approval updates could mask unintended public API growth] → Review the
  exact additive diff and keep the approval test active.

## Migration Plan

The change is additive: existing Health invocations retain their behavior.
Users who configure external evidence can add the documented bindings and
producer context to Health before generating a PR report. Existing legacy
Health artifacts remain reportable as unavailable evidence. Rollback consists
of reverting the additive Health option and orchestration changes; no persisted
artifact migration is required.
