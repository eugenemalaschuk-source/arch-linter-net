## Context

The Architecture Health publication workflow moves an inert badge produced by
unprivileged pull-request CI onto a static public branch after the pull request
has been squash-merged.  That boundary is intentionally trust-sensitive: a
reader must never see a stale healthy result as though it described the current
`main` tip, and failure to assess must be observable as an explicit unavailable
state.

The initial implementation correctly binds a producer artifact to the merged
tree, but it generated the unavailable receipt by rebuilding the CLI in the
privileged workflow, found a required check in any repository ruleset, and
updated the two public files independently.  The CLI badge projector also
accepted a subset of the report-evidence envelope.

## Goals / Non-Goals

**Goals:**

- Make the unavailable public state available without checkout, restore, build,
  or execution of the CLI in the privileged publisher.
- Publish the endpoint and its provenance metadata as one compare-and-swap
  Git commit, only for the current `main` tip.
- Establish the required Architecture Coverage gate from the effective rules
  that apply to `main`, including organization rules.
- Treat report evidence as canonical only when its envelope and every receipt
  required for the badge are complete and mutually consistent.
- Make these invariants executable through workflow-fixture and CLI tests.

**Non-Goals:**

- Recompute architecture Health or interpret producer artifact content in the
  publisher.
- Change the public Shields schema or badge message/color mapping.
- Turn the static branch into a general documentation deployment surface.

## Decisions

### 1. Commit a reviewed unavailable receipt and verify it before merge

`architecture/architecture-health-badge-unavailable.json` is a checked-in,
byte-for-byte CLI output for a missing Architecture Health input.  The
unprivileged CI producer generates the same fallback after it builds the CLI
and compares the files as bytes.  A mismatch fails CI, so `main` only contains
a receipt generated by the reviewed CLI.

The publisher fetches that fixed path at `MAIN_SHA` using the GitHub Contents
API and validates its fixed Shields shape before publication.  It does not
checkout, restore, build, or run the CLI.  Reading through the API keeps the
fallback independent of a runner workspace and of a checkout action failure.

### 2. Use the effective branch-rules endpoint

The publisher asks `GET /repos/{owner}/{repo}/rules/branches/main` for the
active rules effective on `main`, rather than enumerating repository rulesets.
It accepts the gate only when an applicable `required_status_checks` rule has
strict status checks and includes the exact `Architecture Coverage` context.
This includes organization-level policy and cannot be satisfied by an unrelated
release-only ruleset.

### 3. Treat report evidence as an exact envelope for badge inputs

Before reading policy inventory, the CLI requires the top-level Health schema,
the `report_evidence` schema version `2`, exact kind
`architecture-health-report-evidence`, and matching inner and outer gate and
health strings.  Each validation outcome must be an object with a supported
`policy_inventory`; none may be omitted or silently skipped.  Inventories must
still agree with one another and retain their existing schema and non-negative
counter checks.  Any mismatch projects to the explicit unassessable badge.

The positive unit fixture is generated through
`ArchitectureHealthProjector.FormatAsJson(ArchitectureHealthOutcome)`, so the
badge test consumes the production-shaped serializer contract instead of an
ad-hoc JSON subset.

### 4. Atomically publish both public files and prevent stale overwrites

The publisher creates one blob for the endpoint and one for metadata, creates
one tree over the current static-branch tree, then creates one commit containing
both paths.  It checks `refs/heads/main` immediately before the static-branch
ref change; a mismatching event SHA exits successfully without any write.

For an existing publication branch, the new commit has the observed branch tip
as its sole parent and `updateRef(..., force: false)` is the compare-and-swap
boundary.  A concurrent update makes that fast-forward fail instead of
overwriting a newer publication.  For first publication, `createRef` provides
the equivalent no-overwrite boundary.  A lost race produces no partial public
state.

## Risks / Trade-offs

- The Contents API read of the committed receipt is still an external GitHub
  dependency, but it avoids the broader and more failure-prone .NET bootstrap
  path.  The publisher cannot write a replacement badge if GitHub's content API
  itself is unavailable.
- GitHub's ref update API supplies non-force fast-forward semantics rather than
  an explicit expected-SHA parameter.  Parenting the commit at the observed
  publication tip makes a changed tip non-fast-forward, which gives the needed
  compare-and-swap behavior.
- Canonical-envelope validation intentionally rejects older or partial reports.
  Such input becomes visibly unassessable instead of producing an authoritative
  looking badge from incomplete evidence.

## Migration Plan

1. Add the reviewed unavailable receipt and CI byte-comparison.
2. Replace publisher fallback and publication writes with API-read and atomic
   Git-data publication.
3. Tighten CLI evidence parsing and replace its positive fixture with a Core
   serializer result.
4. Run targeted CLI/workflow fixture tests, then the repository's risk-based
   validation and update the pull request without merging it.

## Open Questions

None.  The endpoint, required context name, and unavailable message are fixed
by the existing public contract and review findings.
