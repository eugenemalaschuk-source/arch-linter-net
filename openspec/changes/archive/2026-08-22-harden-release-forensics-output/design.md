## Context

Release-forensics JSON is constructed deterministically in Core and currently
returns a .NET string. The history command writes that string through a general
`TextWriter`, whose process encoding can differ by host. The writer also treats
UTF-16 code units as independent characters, allowing unpaired surrogates to
reach a later encoder.

## Goals / Non-Goals

**Goals:**

- Preserve report JSON bytes as UTF-8 without BOM at the actual history CLI
  stdout boundary.
- Reject malformed UTF-16 before canonical JSON text is returned.
- Convert an unexpected report-rendering Unicode failure to the existing
  separate, fail-closed history diagnostic surface.
- Exercise byte output and Unicode behavior without changing Git analysis.

**Non-Goals:**

- Change Git parsing, evidence ordering, scoring, graph construction, or
  candidate qualification.
- Make Markdown or diagnostics byte-canonical report artifacts.
- Normalize Unicode or add an enrichment provider.

## Decisions

1. `CanonicalJsonWriter` will validate UTF-16 while traversing a string. A
   well-formed surrogate pair is retained as the same scalar; any lone high or
   low surrogate throws a dedicated rendering exception carrying its UTF-16
   offset. This avoids replacement characters and preserves the existing no
   normalization rule. Using an encoder alone was rejected because an arbitrary
   later `TextWriter` can replace malformed content after the canonical writer
   has already claimed success.

2. `ICliConsole` will expose a narrowly scoped canonical-JSON write operation.
   `SystemCliConsole` will write that operation directly to standard output
   bytes through strict `UTF8Encoding(false, true)`. Other console text,
   including Markdown and diagnostics, continues through `TextWriter` so the
   change does not broadly alter CLI presentation behavior. Relying on
   `Console.OutputEncoding` was rejected because it is process-global and can
   be changed by the host.

3. The history handler will catch the dedicated rendering exception and emit a
   stable `report_serialization_invalid` diagnostic with no successful output.
   This keeps reporting failures distinguishable from upstream Git-analysis
   failures while retaining the fail-closed command boundary.

4. Tests will assert UTF-8 bytes directly, verify valid non-BMP scalar output,
   assert both lone-surrogate forms reject, and retain separate successful
   report/diagnostic assertions. Broad snapshots were rejected in favor of
   small, contract-focused vectors that isolate ordering and byte behavior.

## Risks / Trade-offs

- [Raw standard-output write bypasses the ANSI-stripping wrapper] → canonical
  JSON never contains a raw ANSI control sequence; its control characters are
  escaped by the Core writer.
- [A future non-system console may not capture bytes] → the interface default
  retains text capture for test doubles, while the production implementation is
  the only process stdout boundary.
- [The rendering exception is not generated by normal Git evidence] → focused
  tests construct optional enrichment context with malformed internal text to
  prove the defensive contract before future enrichment is introduced.
