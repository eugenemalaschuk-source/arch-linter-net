## ADDED Requirements

### Requirement: Discover direct-child modules from one declared container

The system SHALL support strict and audit module-container contracts that select one declared namespace container and deterministically discover every immediate child namespace containing first-party production types as a module. The contract SHALL govern discovered modules without requiring a hand-maintained layer entry or peer list for each module.

#### Scenario: A new direct child is governed without policy inventory edits
- **WHEN** production code introduces `ArchLinterNet.Cli.Commands.Inspect` beneath a governed `ArchLinterNet.Cli.Commands` container
- **THEN** the module-container contract identifies `Inspect` as a module in the same run
- **AND** no per-command layer or sibling-list policy edit is required for it to be checked

#### Scenario: A nested namespace remains part of its direct parent module
- **WHEN** a type is declared in `ArchLinterNet.Cli.Commands.Inspect.Application`
- **THEN** the contract attributes it to the `Inspect` module rather than treating `Application` as a sibling module

#### Scenario: Discovery is deterministic and visible in diagnostics
- **WHEN** a module-container contract reports a violation or coverage state
- **THEN** its diagnostic identifies the container, the direct module name, and the source and target namespaces where applicable in stable ordinal order

### Requirement: Direct modules are isolated from siblings

A module-container contract SHALL report a dependency whose source and target belong to different discovered direct modules. A published contract or shared-kernel namespace outside the container does not make a direct sibling reference permissible.

#### Scenario: A command implementation imports a sibling command implementation
- **WHEN** a type in `ArchLinterNet.Cli.Commands.Graph` references a type in `ArchLinterNet.Cli.Commands.Validate`
- **THEN** a strict module-container contract fails with a diagnostic naming `Graph` and `Validate`

#### Scenario: Two modules consume a published contract without depending on each other
- **WHEN** two modules reference types in a reviewed namespace outside their module container
- **AND** neither module references the other module's namespace
- **THEN** sibling isolation does not report a cross-module violation

### Requirement: A module declares an exhaustive, feature-first internal shape

A module-container contract SHALL support a declared set of immediate module segments and a production-root policy. The contract SHALL report an undeclared immediate segment containing production types and production types placed at the module root unless each is an explicitly reviewed entry-point exception.

The standard CLI-command profile SHALL recognize `EntryPoint`, `Application`, `Abstractions`, `Models`, and `Exceptions`; `Abstractions`, `Models`, and `Exceptions` are optional until a module has a type of that category. The profile SHALL not include generic `Common`, `Shared`, or `Utils` segments.

#### Scenario: A scaffolded command uses the standard shape
- **WHEN** a command module contains an entry point and a handler generated by the CLI-command profile
- **THEN** the entry point is in `EntryPoint` and the handler is in `Application`
- **AND** the module passes the exhaustive shape check without empty placeholder folders

#### Scenario: An undeclared module bucket is rejected
- **WHEN** a type is added below `ArchLinterNet.Cli.Commands.Inspect.Helpers`
- **THEN** the module-container contract reports that `Helpers` is not a declared module segment

#### Scenario: A reviewed migration exception is explicit
- **WHEN** an existing module root contains a type during migration
- **THEN** audit mode reports it unless the contract names an exact, reasoned entry-point exception
- **AND** strict mode does not accept an unreviewed module-root type

### Requirement: Module-internal dependencies point toward stable contracts and data

The CLI-command profile SHALL enforce these first-party dependency directions for a discovered module: `EntryPoint` may depend on `Application`, `Abstractions`, `Models`, and `Exceptions`; `Application` may depend on `Abstractions`, `Models`, and `Exceptions`; `Abstractions` may depend on `Models`; and `Models` and `Exceptions` have no first-party dependencies. A profile SHALL evaluate only segments that are present.

#### Scenario: An abstraction uses its module's model
- **WHEN** an interface in `Commands.Inspect.Abstractions` references a type in `Commands.Inspect.Models`
- **THEN** the profile accepts the dependency

#### Scenario: An abstraction imports its implementation
- **WHEN** an interface in `Commands.Inspect.Abstractions` references a type in `Commands.Inspect.Application`
- **THEN** the profile reports a dependency-direction violation

#### Scenario: A model imports an application type
- **WHEN** a type in `Commands.Inspect.Models` references a type in `Commands.Inspect.Application`
- **THEN** the profile reports a dependency-direction violation

### Requirement: Generic shared implementation buckets are prohibited

The module-container contract SHALL reject a production namespace segment named `Common`, `Shared`, or `Utils` within a governed module container. Reuse across modules SHALL be introduced only through a reviewed, narrowly named published-contract or shared-kernel namespace outside the container with an owner and a reason in policy.

#### Scenario: A generic shared bucket is introduced
- **WHEN** a type is declared in `ArchLinterNet.Cli.Commands.Shared`
- **THEN** strict module-container governance fails and directs the contributor to a named published boundary or independently owned capability

#### Scenario: A named shared kernel is explicitly governed
- **WHEN** a policy classifies and governs `ArchLinterNet.Cli.Integration.OutputFormatting` as an owner-reviewed integration boundary
- **THEN** modules may depend on that boundary according to its explicit dependency contract
- **AND** the namespace is not treated as an unbounded replacement for sibling dependencies
