# Large-solution benchmark foundation

This directory owns the public-safe, synthetic benchmark contract for v0.9
performance and scale work. The corpus is generated by the focused Core test
infrastructure under `tests/ArchLinterNet.Core.Tests/Benchmarking`; it is not a
product API and its hardware-sensitive matrices are never part of `make test`
or `make acceptance`.

## Workload catalog

`BenchmarkWorkloadDefinition` produces a `BenchmarkWorkloadManifest` using
`large-solution-benchmark/v1`; its standalone contract is
`large-solution-workload-v1.schema.json`. A manifest names one deterministic shape,
compilation mode, workflow, project graph, inventory, pull-request change shape,
and independent dimensions. Supported graph shapes are:

- `Linear` / deep dependency chain;
- `WideFanOutFanIn`;
- `Diamond` / alternate paths;
- `Dense`;
- `CyclicScc`;
- `ManyProjectsFewTypes` and `FewProjectsManyTypes`.

Project, type, source-file, reference/edge, layer/selector, contract/finding,
source-root, and PR-change dimensions are recorded in the manifest and derived
inventory. Type count is `projects × types_per_project`; source roots distribute
those types and do not multiply them. `selector_predicate_terms_per_layer`
materializes distinct CEL terms, and
`selector_predicate_evaluation_count = projects × types × layers × terms`.
Finding candidates select distinct concrete synthetic types, so
`finding_candidate_count` and `canonical_identity_candidate_count` describe
the actual candidate work rather than N contracts applied to every type.
Contracts use the workload-level `contracts_per_workload` dimension and are
not multiplied by `source_root_count`; source-root scaling therefore remains
independent of contract work. Derived int32 counters fail closed on overflow,
and the schemas bound both input dimensions and deterministic inventory counts.
Reference density adds forward edges for acyclic shapes;
cycles are reserved for explicitly cyclic shapes. In v1, `CyclicScc` is a
structural-only descriptor: the fixture rejects project-based compilation of
that shape because ordinary MSBuild project-reference cycles are not buildable.
An external IL/assembly producer is required before it can become an executable
staged benchmark.

Optional `ignore_rule_count`, `metric_rule_count`, and `report_rule_count`
dimensions default to zero and are omitted from canonical serialization when
unset, preserving identities for existing manifests. When set, ignore entries
and metric declarations are emitted into the synthetic policy, and report-rule
descriptors are written to `.benchmark/report-rules.json`. Their inventory
counts are independent of project, type, and source-root dimensions.
The v2 workload generator keeps method-body rules outside ordinary dependency
contracts and uses topology-type metrics so each metric declaration produces a
deterministic, non-empty result.
Method-body rules contribute only to `method_body` contracts; they do not add
ordinary dependency contracts. Metric workloads execute `Measure()` on the
prepared analysis snapshot and retain each metric ID, kind, value, contributor
count, and canonical result digest in the optional `metric_work` evidence field.
This output is separate from the `metric_budgets` contract-family counter in
`analysis-profile/v1`.

Report-rule workloads use exactly 32 SARIF findings at every declared rule
scale. Findings cycle through every declared rule so serialization comparisons
vary rule-table size without also varying result volume.

An optional `contract_layer_graph` describes executable type references among
synthetic namespaces inside a normal project fixture. `dense_dag` creates every
forward edge, `layered_dag` creates a forward chain, and
`strongly_connected_with_acyclic_tail` creates a two-layer SCC followed by a
one-way tail. The fixture emits both `strict_cycles` and
`strict_acyclic_siblings` policy entries for these layers. This graph is
independent from project references: `CyclicScc` remains structural-only and
continues to fail closed for compilation.

`RealMsBuild` workloads own candidate compilation through an explicit restore and
build. `StagedAssemblies` workloads perform that external compilation before the
analysis run, copy the resulting DLLs into `.benchmark/staged-assemblies`, and
write an ArchLinterNet build receipt for each input. A fixed compiler path map
keeps those staged DLLs and receipts stable across temporary fixture roots. The staged policy resolves
those DLLs through `analysis.target_assemblies` and `assembly_search_paths`, so
preparation cost is not attributed to the analyzer. The materializer creates only
bounded synthetic fixtures; the very-large catalog entry is staged and does not
silently turn a normal test run into a large build.

The materialized-input SHA-256 uses fixture-relative paths and bytes for source,
project, policy, solution, and workload metadata. It excludes the temporary root,
generated `bin`/`obj` outputs, analysis caches, and per-run profile/output files.
Staged assemblies, their build receipts, and the staged manifest remain included
because analysis consumes those files directly.

## Evidence

`benchmark-evidence/v1` wraps raw `analysis-profile/v1` JSON in the
`benchmark-evidence-v1.schema.json` envelope. Each run retains workload identity,
canonical-result SHA-256, deterministic work counts, cache/prepared mode,
environment identity, and resource measurements. Unavailable CPU, allocation,
peak-memory, cache, or prepared-state values are represented explicitly; zero
is never used as a substitute for unavailable data.

The optional audit extension records fixed-key Core work counters, independent timer intervals,
observer overhead, metric results, and source/runner/materialized-input provenance. Timer intervals may overlap and
are never subtracted to infer process startup or analyzer time. The extension leaves
`analysis-profile/v1` unchanged, and old evidence omits the optional fields.

Complexity observations record the scale variable, multiple size points,
deterministic work counters, the current/target work model, and an explicit
`NotReproduced` disposition when the suspected hotspot does not appear. An
optimization candidate must carry the pre-implementation expected-effect
contract: measured phase share, local and end-to-end estimate, cold/warm and
memory/storage trade-offs, issue-specific success threshold, kill criterion,
and uncertainty. A slow sample alone does not authorize an optimization.

## Issue #493 preparation-reuse contract

This is a pre-implementation decision gate, not evidence that a persisted
prepared-analysis implementation exists. The same candidate workload is
compared across independent one-shot processes, one process serving safe
projections from one immutable snapshot, and a persisted prepared-state
expected-effect model.

The current full-governance command mix is represented explicitly in the
workload manifest and evidence `workflow`: strict and audit validation,
no-new-debt, Architecture Health, and the current-side change snapshot are
the required command families. Topology, measure, baseline/reference, and
public-API projections are optional and must appear only when the declared
workflow actually invokes them. A command description must never imply an
unmeasured projection.

Every sample preserves the candidate preparation boundary. `real_ms_build`
means the fixture owns the restore/build and records the receipt-backed build
boundary; `staged_assemblies` means the build occurred before analysis and the
fixture verifies the exact copied assemblies and receipts before analysis
starts. These are two preparation shapes for the same policy semantics, not
unrelated workloads.

Candidate and base/reference revision samples are attributed separately. Base
preparation and fact counters are not reusable candidate work and are excluded
from candidate savings or prepared-state break-even calculations. Cache-disabled,
cache-miss, and exact-request cache-hit modes are also distinct: work avoided by
an `analysis-cache/v1` hit is not counted again as prepared-analysis benefit.

## Methodology and reuse

Downstream issues #503, #655, #675, and #493 select or extend these workload
descriptors rather than creating competing scale frameworks. Measurements should
compare at least three useful sizes when practical, separate cold and warm
behavior, distinguish cache-disabled/miss/hit and prepared/unprepared modes,
and verify canonical findings, identity, ordering, completion, and exit
semantics across equivalent modes. Timing and memory values are observations
for the declared environment, not universal SLAs. For #493, the explicit
multi-command matrix is a manual measurement and must not run from the normal
test or acceptance gate; deterministic schema/contract tests remain in that
gate.

Shared History scale shapes live in `workload-catalog.json`: sparse and dense line churn (#1138),
sparse and overlapping task occurrences (#1139), disconnected and dense co-change components
(#1140), and long rename-chain and merged-DAG ancestry queries (#1141). Each listed family has
three scale points with independently named dimensions. The test-only
`BenchmarkHistoryInputFactory` materializes these as canonical `benchmark-history-input/v1` data
with stable input and expected-shape-summary SHA-256 identities. Its ordinary tests check line edit
counts, task occurrences, graph components, and ancestry answers against the generated records.
The merged-DAG fixture has separate side branches that fork from the mainline and rejoin through
two-parent commits; long rename-chain fixtures contain continuous path-change events. Tests verify
both structures and derive query answers from the parent-edge graph.
Owning History tasks remain responsible for running their production algorithm, recording its
operation counts and resources, and hashing the canonical algorithm output.

The #1123 audit adds independent three-point project, source-file, contract, ignore, finding,
metric, report-rule, and method-body families, plus three-point dense DAG, layered DAG, and
SCC-with-acyclic-tail graphs. Deterministic checker, counter, and report checksum assertions run in
ordinary Core tests. The environment-sensitive repeated matrix is explicit and writes
issue-scoped `benchmark-evidence/v1` documents; it is not part of normal tests or acceptance.

Committed artifacts contain synthetic `Synthetic.ProjectNNN` identities only;
private adopter names, repository URLs, proprietary topology, and raw private
CI logs are out of scope.
