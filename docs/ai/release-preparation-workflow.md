# Release Preparation Workflow

Use this workflow to prepare the repository-side content and reviewed release-scope authority for a concrete ArchLinterNet release.

This workflow owns **release preparation**, not package publication. It turns repository facts into a reviewed release story, release-note categorization inputs, a release-scope declaration, validation evidence, and one pull request. The maintainer publication procedure remains owned by `docs/reference/release-process.md`.

## Input

The user normally supplies one of:

- an explicit version such as `0.7.4` or `v0.8.0`;
- a request for the next `patch`, `minor`, `major`, or `preview` release;
- a release-story URL plus an explicit or derivable target version.

Normalize an optional leading `v` only for comparison. Use package/release targets without `v` and Git tags with `v`, matching the repository release process.

If the user asks for the next release scenario rather than an exact version, derive the target only from the current SemVer-compatible tag history and the rules in `docs/reference/release-process.md`. Do not invent a version from milestone names.

If the target cannot be derived unambiguously from repository facts, report the exact ambiguity instead of writing speculative release authority.

## What “release content” means in this repository

Release-specific history is not maintained as a committed version-named changelog page. The durable human-facing release record is the GitHub Release generated by the release workflow.

Repository-side release preparation consists of:

1. a reviewed release story that states the intended product delta and publication contract;
2. correct labels on the PRs/issues that feed `.github/release.yml` categories;
3. `tools/release/scopes/<version>.json` as the reviewed Checkpoint B release authority;
4. shipped-declaration regression coverage;
5. exact local/CI validation evidence in the preparation PR;
6. an explicit handoff to the maintainer-only dry-run/publication procedure.

Do **not** create a new evergreen docs page merely to record one release. Update evergreen user documentation only when the product behavior or adoption guidance itself changed and the owning implementation/release backlog requires that update.

## Sources of truth

Read these before authoring release content:

- `AGENTS.md` and applicable harness instructions;
- `docs/reference/release-process.md`;
- `.github/release.yml`;
- `tools/release/scopes/` and the current release-scope schema/consumer tests;
- the latest relevant published GitHub Release and SemVer tag;
- the candidate commit/ref that would be released;
- merged pull requests, closed issues, and commits in the candidate delta;
- the existing release story, when one exists;
- materially linked bug/feature/release issues and their acceptance evidence.

Milestone membership is a **discovery aid**, never release authority. Mutable issue text or a milestone cannot substitute for the reviewed release-scope declaration selected by the immutable candidate version.

## Mandatory lifecycle

Execute these phases in order:

1. Establish release identity and candidate.
2. Reconstruct the factual candidate delta.
3. Define or reconcile the release story.
4. Audit release-note categorization.
5. Author the reviewed release-scope declaration.
6. Update shipped-declaration regression coverage.
7. Validate the preparation change.
8. Open one release-preparation pull request.
9. Stop at the publication boundary and report the maintainer handoff.

Do not skip directly to a JSON declaration before understanding the candidate delta.

## 1. Establish release identity and candidate

Determine and record:

- `RELEASE_TARGET`, without the `v` prefix;
- the intended release scenario: `preview`, `patch`, `minor`, or `major`;
- the previous relevant published SemVer release/tag;
- the exact candidate branch/ref and commit SHA;
- whether the target tag/GitHub Release already exists;
- whether an existing `tools/release/scopes/<RELEASE_TARGET>.json` already authorizes the target;
- whether a release story already exists.

Fail closed on conflicting release identity. Never overwrite an existing tag, GitHub Release, or incompatible declaration merely because the requested version matches.

### Patch-release guard

A patch release is normally corrective maintenance, not a vehicle for unrelated next-minor work.

Before authoring a patch declaration, prove that the candidate can actually represent the intended patch scope. If `main` already contains unrelated feature work that would also be shipped, do not hide that fact with an artificially narrow declaration. Report the release-line/candidate blocker and require the repository's reviewed release strategy (for example an appropriate maintenance ref or a different version decision).

The release-scope declaration describes and authorizes the real immutable candidate; it does not subtract bytes already present in that candidate.

## 2. Reconstruct the factual candidate delta

Compare the previous release tag/ref with the candidate commit and inspect the actual merged work.

Build a compact evidence inventory containing, where applicable:

- merged PR number and title;
- owning issue/story;
- merge commit or squash commit;
- user-visible behavior affected;
- whether it is a bug fix, feature, documentation change, dependency update, CI/release-only change, or internal refactor;
- whether the change is intended product scope, already-delivered context, explicitly excluded/non-blocking work, or unrelated candidate content that blocks the intended release shape;
- current release-note labels.

Do not classify scope from commit-title wording alone. Follow linked issues/PRs and inspect enough code/docs/evidence to understand what is actually being shipped.

For a maintenance release, explicitly identify the externally discovered correctness/regression defects being shipped and the merged fixing PRs. For a feature release, reconcile the release story/backlog with what is actually present in the candidate.

## 3. Define or reconcile the release story

Reuse an existing release story when it accurately owns the requested target. Otherwise create one before authoring the scope declaration.

Use the repository backlog-governance conventions and include at least:

- `Goal`;
- `Work type`;
- `Context`;
- `Release scope` when the delta is non-trivial;
- `What to do`;
- `Manual tasks`;
- `AI-friendly tasks`;
- `Estimate`;
- `Acceptance criteria`;
- `Validation`;
- `Non-goals`.

The story must state the intended product delta precisely enough that a reviewer can decide whether the release-scope declaration is truthful.

### Patch / maintenance story

For a corrective patch release, normally state:

- the previous published version and discovery context;
- each defect being shipped and the merged fix that resolves it;
- that no unrelated feature scope is intended;
- any combined regression proof needed before publication;
- that release-scope authoring/evidence wiring is AI-friendly;
- that workflow dispatch, public publication, and post-publication verification remain maintainer actions.

Do not assume one defect: v0.7.2 shipped two defects, while v0.7.3 shipped one.

### Minor / major story

For a broader release, enumerate the reviewed release intent rather than treating every item in a milestone as mandatory. Distinguish:

- **required** product/release items that must be complete for this candidate;
- **excluded** items that are explicitly non-blocking for this release;
- **delivered context** that is already complete and useful to record but is not an open blocker.

This distinction is reflected in the v0.7.0 release declaration and must remain available for future releases.

## 4. Audit release-note categorization

Read `.github/release.yml` and verify that merged PRs intended for the public release notes have the labels required for the desired category.

Current category semantics are repository configuration, not hard-coded skill policy. Re-read the file on every release.

Typical examples in the current configuration include:

- `bug` / `fix` → Fixes;
- `enhancement` / `feature` → Features;
- `documentation` → Documentation;
- `ci` → CI/CD;
- `dependencies` → Dependencies;
- `breaking-change` → Breaking Changes;
- `ignore-for-release` → excluded from generated notes.

When repository evidence makes the intended category unambiguous, add the missing existing label before publication. Never invent a new label merely to force a category.

Check the full intended release delta, not only the release-scope PR itself. A correctly written scope JSON does not repair incorrectly categorized public notes.

Do not commit generated release notes. The release workflow generates them and the GitHub Release is the durable release-history record.

## 5. Author the reviewed release-scope declaration

Create `tools/release/scopes/<RELEASE_TARGET>.json` only after the release story and factual scope are coherent.

Follow the current schema and neighboring declarations rather than copying stale field assumptions. At the time this workflow was authored, stable declarations use:

```json
{
  "schema": "checkpoint-b-release-scope-declaration/v2",
  "declaration_id": "...",
  "release_target": "X.Y.Z",
  "story": 123,
  "_comment": ["..."],
  "required_items": [],
  "excluded_items": [],
  "delivered_items": []
}
```

Rules:

- `release_target` must exactly match the immutable candidate version the declaration is meant to authorize;
- `story` must point to the reviewed release story;
- `declaration_id` must be stable and meaningful for the release intent;
- comments explain intent and authority, not mutable implementation guesses;
- `required_items` represent reviewed required product/release delta;
- `excluded_items` represent explicitly reviewed non-blockers/exclusions when needed;
- `delivered_items` record already-delivered context when needed;
- do not infer required items from milestone membership;
- do not silently omit real candidate changes merely because they are inconvenient for the desired release narrative;
- do not create duplicate declarations for the same `release_target`.

For corrective patch releases, empty `excluded_items` and `delivered_items` are normal when the scope is simply the reviewed bug-fix set. For richer releases, use all three lists when the reviewed intent requires them.

## 6. Update shipped-declaration regression coverage

Find the existing release-scope regression test that loads the shipped declarations and asserts the authorized target set/story/item identities.

Update it for the new declaration so the repository proves at least:

- every shipped declaration has a unique target;
- the new target is included in the reviewed target set;
- the story number is correct;
- required issue identities are correct;
- excluded/delivered identities or emptiness match reviewed intent.

Follow the current test structure; do not create a second competing declaration inventory unless the existing test architecture genuinely requires refactoring.

## 7. Validate the preparation change

OpenSpec is normally **not applicable** to release-content/scope authoring because it does not change product capability semantics. Say so explicitly in the PR. If the preparation work unexpectedly changes a public capability, schema, release-pipeline contract, or documented product guarantee, stop treating it as content-only work and follow the normal OpenSpec lifecycle for that additional change.

At minimum for a normal declaration-only release preparation:

1. run the complete release-tool test suite containing the release-scope evidence tests, currently `python -m pytest tools/release/tests/` using the repository's active virtual environment/interpreter;
2. inspect the final declaration and regression-test diff;
3. verify the release story and declaration agree exactly;
4. verify intended public-note labels against `.github/release.yml`;
5. verify no generated changelog/release-note page was added;
6. verify no package/version property was changed merely to force the release version.

If release scripts, workflow logic, schemas, packaging, or publication authority are modified beyond adding a declaration/test entry, escalate validation to the repository's release/publication risk tier and run the broader release-specific gates required by those files.

Record exact commands and observed results. Never reuse pass counts from an older release.

## 8. Branch, commit, and pull request

Never prepare release authority directly on `main`.

Use the release story as the branch/PR owner. Preserve the repository's one-issue/one-branch/one-PR invariant for the preparation change.

For the established declaration-only maintenance shape, prefer a title consistent with recent releases:

```text
[TASK][HYBRID] Release: Add v<RELEASE_TARGET> release-scope declaration
```

Use a more accurate title only when the preparation PR genuinely includes additional reviewed repository-side release work.

The PR must target `main`, close the release story when the PR completes all AI-friendly preparation owned by that story, and contain these sections:

- `Summary`;
- `Architecture notes`;
- `Scope / non-goals`;
- `Tests run`;
- `Risks / follow-ups`.

In the PR body:

- state whether the release is corrective maintenance or broader feature scope;
- name the exact required issues/fixes/features;
- state that the declaration follows the current Checkpoint B schema;
- list exact validation results;
- state `OpenSpec: not applicable` with the reason when true;
- state the publication handoff explicitly;
- mention release-note label corrections made or confirm that intended PRs were already categorized correctly.

Do not merge the PR unless the user explicitly requests merge.

## 9. Publication boundary

Release preparation is complete when the reviewed repository-side authority PR is ready/merged according to the user's request. It does **not** silently publish the release.

The canonical maintainer procedure in `docs/reference/release-process.md` requires:

1. a manual dry run with publication disabled;
2. review of generated release notes, package artifacts/metadata/README and release evidence;
3. a separate manual public publication run;
4. post-publication verification of NuGet.org, GitHub Release/assets/provenance, and GitHub Pages.

Do not trigger publication merely because the preparation PR is green. Do not create tags or GitHub Releases manually as a shortcut around the workflow.

If the user explicitly asks to proceed with publication, re-read `docs/reference/release-process.md` at that time and follow its current maintainer/manual boundary. If the active harness cannot perform an authorized required UI/manual action, report that exact remaining action instead of pretending it ran.

## Reference patterns

Use recent releases as behavioral examples, not immutable templates:

- v0.7.1: corrective maintenance release with one release-scope declaration and no feature scope;
- v0.7.2: corrective maintenance release with two independent externally discovered regressions and combined candidate proof;
- v0.7.3: corrective maintenance release with one externally discovered correctness defect;
- v0.7.0: broader release declaration demonstrating `required_items`, `excluded_items`, and `delivered_items` together.

Always re-read the current files/issues because schemas, labels, tests, and release process can evolve.

## Completion report

After opening the preparation PR, report:

- target version and scenario;
- previous release/tag and candidate commit;
- release story URL;
- required/excluded/delivered scope summary;
- release-note labels checked or changed;
- branch and final commit;
- PR URL;
- exact validation performed and results;
- OpenSpec applicability result;
- any factual blocker or risk;
- the explicit maintainer publication handoff.

Never report the release itself as published unless publication and post-publication verification actually occurred.
